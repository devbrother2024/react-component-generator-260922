# TDD Rule

> **경고: 이 규칙은 Rigid다.** 상황에 맞게 완화하거나 변형하지 마라. 예외가 필요하다고 느껴진다면 그것은 "적용 불필요 대상"에 해당하는지 먼저 확인하라는 신호이지, 사이클을 생략해도 된다는 신호가 아니다.

## 0. 우선순위 조항

이 파일은 **fallback 기본값**이다. 프로젝트 루트 또는 하위 `CLAUDE.md`/`AGENTS.md`에 TDD 관련 규칙이 명시되어 있다면 그것을 우선 적용하고, 이 파일은 그 규칙이 다루지 않는 부분에만 보충으로 적용한다.

## 1. 적용 기준

### TDD를 반드시 적용해야 하는 대상

- **비즈니스 로직** (도메인 규칙, 계산, 상태 전이)
- **API** (엔드포인트 핸들러, 요청/응답 검증, 에러 처리)
- **유틸리티 함수** (순수 함수, 데이터 변환/파싱)
- **버그 수정** (수정 전에 실패하는 재현 테스트부터 작성)

### TDD가 불필요한 대상

- **타입 정의** (interface, type alias 등 런타임 동작이 없는 선언)
- **설정 파일** (tsconfig, eslint config, vite config 등)
- **순수 UI 마크업** (스타일/레이아웃만 있고 로직이 없는 컴포넌트)
- **SQL/마이그레이션 스크립트**

애매한 경우 "런타임에 분기하거나 실패할 수 있는 로직이 있는가"로 판단하라. 있으면 적용 대상이다.

## 2. RED-GREEN-REFACTOR 사이클

### RED

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 욱여넣지 마라.
- 작성한 테스트는 **반드시 실행해서 실패를 눈으로 확인**한다. 실행하지 않고 넘어가는 것은 RED가 아니다.
- 실패 이유는 반드시 **"기능이 아직 구현되지 않음"**이어야 한다. 오타, import 누락, 문법 오류로 인한 실패는 RED가 아니라 버그다 — 고치고 다시 실행하라.

### GREEN

- 테스트를 통과시키는 데 **필요한 최소한의 코드만** 작성한다.
- **YAGNI**: 지금 테스트가 요구하지 않는 기능, 파라미터, 분기를 미리 만들지 마라.
- 코드를 작성한 뒤 **신규 테스트와 기존 테스트 전체가 통과**하는지 확인한다. 일부만 실행하고 넘어가지 마라.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출 등 **구조 개선만** 수행한다.
- 리팩터링 전후로 **모든 테스트가 green을 유지**해야 한다. 하나라도 깨지면 되돌리고 다시 접근하라.
- 이 단계에서 **새로운 동작을 추가하지 마라.** 새 동작이 필요하다고 느껴지면 그것은 다음 사이클의 RED다.

### 반복

REFACTOR가 끝나면 다음 동작에 대한 **RED로 돌아간다.** 모든 동작을 커버할 때까지 사이클을 반복한다.

## 3. 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성한 것을 발견하면, **그 코드를 삭제하고 RED부터 다시 시작**한다.
- "일단 참고용으로 남겨둔다", "테스트만 나중에 채워 넣는다" 같은 절충은 **금지**한다. 순서를 어긴 코드는 존재 자체가 위반이다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트가 필요 없다" | 단순한 로직일수록 테스트 작성 비용도 낮다. 비용이 낮은데 안 할 이유가 없고, 단순해 보이는 코드가 나중에 복잡해질 때 회귀를 잡아주는 것도 이 테스트다. |
| "나중에 추가하겠다" | "나중"은 오지 않는다. 지금 통과하는 코드에 나중에 테스트를 끼워 맞추면 테스트가 구현을 검증하는 게 아니라 구현을 베끼는 것이 된다. |
| "시간이 없다" | RED-GREEN-REFACTOR는 디버깅 시간을 줄여서 총 소요 시간을 단축한다. 시간이 없다는 것은 테스트를 생략할 이유가 아니라 사이클을 더 잘게 쪼개야 한다는 신호다. |
| "삭제하면 낭비다" | 순서를 어기고 작성한 코드는 검증되지 않은 코드다. 남겨두면 "낭비"가 아니라 "미검증 부채"가 남는 것이다. 삭제 후 RED부터 다시 만드는 코드는 어차피 금방 재작성된다. |
| "프로토타입이다" | 프로토타입도 런타임에 실패할 수 있는 로직을 담고 있다면 적용 대상이다. 진짜 버릴 코드라면 애초에 이 규칙이 다루는 "비즈니스 로직/API/유틸/버그수정"에 해당하지 않을 것이다. |
