# commit: 변경사항 분석 후 컨벤션 커밋

현재 git 저장소의 변경사항을 분석해 논리적 단위로 나누고, 컨벤션에 맞는 한국어 커밋 메시지를 작성해 **승인 절차 없이 바로** 커밋한다. 이 스킬이 트리거되었다는 것 자체가 커밋에 대한 사용자 승인으로 간주한다.

## 워크플로우

### Step 0: 저장소 지침 확인

저장소 루트(또는 수정 파일에 가장 가까운 디렉토리)에 `AGENTS.md`나 `CLAUDE.md`가 있으면 읽고, 커밋 메시지 형식이나 컨벤션이 명시돼 있으면 그것을 최우선으로 따른다. 명시된 지침이 없으면 아래 기본 규칙을 따른다.

### Step 1: 변경사항 분석

- `git status`로 변경/추가/삭제된 파일 목록을 확인한다.
- `git diff`(스테이징 안 된 변경)와 `git diff --staged`(스테이징된 변경)로 실제 내용을 확인한다.
- `git log --oneline -20` 등으로 최근 커밋 메시지 스타일을 확인하고, 기존 스타일이 있으면 그것과 맞춘다(접두사 표기, 어미, 언어 등).

### Step 2: 논리적 단위로 분류

- 서로 관련 없는 변경(예: 기능 추가 + 포맷팅, 두 개의 별개 버그 수정)은 별도 커밋으로 나눈다.
- 하나의 목적으로 묶이는 변경(리팩터링에 따른 여러 파일 수정 등)은 하나의 커밋으로 묶는다.
- 특별히 나눌 이유가 없다면 하나의 커밋으로 묶어 진행한다. 분류 판단은 직접 내리고 사용자에게 확인을 구하지 않는다.

### Step 3: 커밋 메시지 작성

각 커밋 단위에 대해 한국어 커밋 메시지를 작성한다.

형식: `<type>: <요약>`

- `type`은 다음 중 변경 성격에 맞는 것을 고른다:
  - `feat`: 새 기능 추가
  - `fix`: 버그 수정
  - `refactor`: 동작 변화 없는 구조 개선
  - `chore`: 빌드/설정/의존성 등 잡무성 변경
  - `docs`: 문서만 변경
  - `test`: 테스트 코드 추가/수정
  - `style`: 포맷팅 등 코드 의미에 영향 없는 변경
- `요약`은 한 줄로, 무엇을 했는지가 아니라 변경의 핵심을 간결한 한국어로 쓴다(예: "커밋 메시지 검증 로직 추가").
- 변경이 커서 한 줄로 부족하면 본문을 추가한다. 본문은 "무엇"보다 "왜"에 집중하고, 코드만 봐도 알 수 있는 내용은 반복하지 않는다.
- 여러 커밋으로 나눴다면 커밋마다 이 형식을 따로 적용한다.

### Step 4: 자동 커밋

승인을 구하지 않고 바로 진행한다. 커밋 단위별로 해당 파일만 `git add`로 스테이징한 뒤 작성한 메시지로 커밋한다.

- `git add -A`나 `git add .`처럼 범위를 특정하지 않는 스테이징은 피하고, 분류된 파일만 명시적으로 추가한다.
- 스테이징 전 `git status`/변경 내용으로 의도치 않은 파일(시크릿, `.env`, 빌드 산출물 등)이 섞여 있는지 확인한다. 그런 파일이 발견되면 그것만 제외하고 진행하되, 무엇을 왜 제외했는지 커밋 후 보고에 남긴다.
- 커밋 완료 후 `git log`/`git status`로 결과를 확인하고, 커밋 단위별 메시지와 포함 파일을 사용자에게 보고한다(사후 보고이며 실행을 막지 않는다).
- 원격에 push하는 것은 이 스킬의 범위가 아니다. 사용자가 별도로 요청하면 그때 진행한다.
